# 0.5.0 JVM binary compatibility

`0.5.0` is still unreleased. This note records the compatibility decision
against the published `0.4.0` artifacts and is part of the release gate.

## Decision

The stable JVM entry points are preserved with source-compatible overloads:

- `LeaderProperties` retains the published ten-argument constructor, copy
  method, and first ten `componentN` methods.
- `LeaderObservabilityProperties` retains its two-argument constructor and
  copy method.
- `HazelcastLock` and `HazelcastSuspendLock` retain their two-argument
  constructors.
- Spring metrics, Actuator endpoint, and AOP property bridges retain the
  previously published JVM methods where the underlying contract remains
  stable.

The repeatable check is:

```bash
./gradlew checkBinaryCompatibility --no-configuration-cache --console=plain
```

It compares all sixteen publishable library artifacts with the `0.4.0`
Maven Central baseline. `examples/*`, `benchmark`, and the BOM are excluded
because they are not published runtime artifacts.

## Classification

The gate reports every japicmp result. Only the following are classified as
intentional implementation noise:

- Kotlin compiler-generated inline/lambda classes and AspectJ closure classes;
- Kotlin compiler-generated synthetic accessor methods (`access$...`) that
  expose private implementation details to another generated class;
- JVM bridge methods emitted for generic Kotlin overrides;
- classes under `io.bluetape4k.leader.*.internal`.

Any other `!` report fails the command and must be either restored or added to
this note with an explicit migration decision. Serializable model
`serialVersionUID` diagnostics are retained in the raw report as metadata
changes; they are not API-entry-point removals and do not make the binary gate
pass silently.

No intentional public recompile requirement is currently approved for
`0.5.0`.
