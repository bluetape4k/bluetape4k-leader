# 배운 교훈 - Exposed R2DBC DB-time availability 복구 경계

## 맥락

Issue #667의 `useDbTime=true` 경로는 DB server time 조회 실패 후 그룹 선출을
fail-closed로 유지해야 합니다. R2DBC delete-only unlock은 소유 토큰 삭제만
수행하므로 `CURRENT_TIMESTAMP`가 정상이라는 증거를 만들지 못합니다.

## 원인

`unlockAndReport()`가 delete 성공 뒤 항상 `markAvailable()`을 호출해, DB-time
조회가 실패한 이후에도 availability 상태를 다시 열 수 있었습니다. 삭제 성공과
시간 primitive 성공을 같은 health signal로 취급한 것이 원인입니다.

## 결정

min-lease update처럼 `CURRENT_TIMESTAMP`를 실제로 조회한 unlock 경로에서만
availability를 회복합니다. delete-only release는 token row를 정리하지만
availability 상태를 변경하지 않습니다. DB-time ownership 연산의 성공이 다시
관측될 때까지 admission은 보수적으로 닫힌 상태를 유지합니다.

## 검증

- 회귀 테스트 RED: H2에서 delete-only unlock 후 `[true]`가 기록되어 실패
- 회귀 테스트 GREEN: 동일 H2 테스트 통과
- `unlockAndReport()`의 delete-only 경로와 min-lease time-query 경로를 분리 확인

## 향후 지침

DB lock의 상태 회복 signal은 SQL 성공 여부가 아니라 ownership에 필요한
authoritative time primitive의 성공 여부에 연결해야 합니다. 삭제·정리 작업은
리소스를 회수할 수 있어도 시간 기준이 복구됐다는 증거로 사용하지 않습니다.
